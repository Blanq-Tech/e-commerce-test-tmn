# Архитектура: масштабирование до 10 000 проверок/день

Условие: 500 товаров × 20 запросов = **10 000 проверок в день**. Результаты — в PostgreSQL.
Если позиция упала ниже 50 — алерт в Telegram. Сервис не должен блокироваться.

## 1. Технологии и почему именно они

| Слой | Технология | Почему |
|------|-----------|--------|
| Сбор данных | **Playwright (Chromium, async)** | Реальный браузер проходит антибот Ozon (JS-челленджи, фингерпринт), где «голый» HTTP отваливается на 403. |
| Очередь задач | **Celery + Redis** (либо arq) | Распределяем 10k задач по воркерам, ретраи, расписание (Celery Beat — раз в сутки/час). |
| Планировщик | **Celery Beat / cron** | Раскладывает 10k задач равномерно по окну, а не «пачкой». |
| Хранилище | **PostgreSQL** | Истории позиций, дедуп, аналитика трендов. |
| Кеш/брокер | **Redis** | Брокер Celery + кеш «прокси на cooldown» + дедуп задач. |
| Прокси | **Резидентные RU прокси** (пул 50–100 IP) с ротацией | Датацентровые IP Ozon банит быстро; резидентные живут дольше. |
| Алерты | **Telegram Bot API** | Дешево, мгновенно, легко интегрировать. |
| Оркестрация | **Docker + docker-compose / k8s** | Изоляция, горизонтальное масштабирование воркеров. |
| Мониторинг | **Prometheus + Grafana**, **Flower** | Метрики успешности, доля блокировок, латентность; Flower — состояние Celery. |

## 2. Устойчивость (антибан)

Главная боль — антибот Ozon. Что делаем:

- **Пул резидентных прокси 50–100 IP**, ротация по задачам. После 403/таймаута —
  IP на cooldown (в проекте уже реализовано в `proxy.py`).
- **Rate limiting на IP**: не больше ~1 запроса в 8–15 с с одного IP, джиттер.
  При 80 живых IP это безопасно даёт 10k проверок за несколько часов.
- **Реальные браузерные сессии**: Playwright + ротация User-Agent, viewport, locale,
  лёгкий stealth (скрываем `navigator.webdriver` и пр.).
- **Прогрев сессий**: заход на главную/категорию перед поиском — поведение ближе к живому.
- **Экспоненциальные ретраи** со сменой прокси и паузами.
- **Деградация**: при всплеске блокировок снижаем частоту (адаптивный rate limiter),
  а не долбим в стену.
- **Распределение во времени**: 10k задач не «в полночь пачкой», а размазаны окном.

Безопасные лимиты (оценка):
- 1 IP: ~6–8 запросов/мин максимум, целимся в 4–5.
- На задачу (до 100 позиций) обычно 1–3 страницы выдачи = 1–3 запроса.
- 80 IP × 5 задач/мин ≈ 400 задач/мин теоретически; реально берём 20–30%
  запаса → ~100–120 задач/мин → 10k за ~1.5–2 часа.

## 3. Схема

```
                ┌──────────────┐     раз в сутки
                │ Celery Beat  │ ───────────────► кладёт 10k задач в очередь
                └──────────────┘
                        │
                        ▼
                ┌──────────────┐
                │    Redis     │  (брокер + cooldown прокси + дедуп)
                └──────┬───────┘
            ┌──────────┼───────────┐
            ▼          ▼           ▼
       ┌─────────┐ ┌─────────┐ ┌─────────┐
       │ worker1 │ │ worker2 │ │ workerN │   (Playwright + ProxyPool)
       └────┬────┘ └────┬────┘ └────┬────┘
            └──────┬─────┴───────────┘
                   ▼
            ┌─────────────┐      позиция < 50 ?
            │ PostgreSQL  │ ───────────────► ┌───────────────┐
            │ (история)   │                  │ Telegram Bot  │ → алерт
            └─────────────┘                  └───────────────┘
                   ▲
                   │ метрики
            ┌─────────────┐
            │ Prometheus  │ + Grafana + Flower
            └─────────────┘
```

Модель данных (упрощённо):

```sql
CREATE TABLE rank_check (
    id           BIGSERIAL PRIMARY KEY,
    query        TEXT        NOT NULL,
    sku          TEXT        NOT NULL,
    position     INT,                 -- NULL = not_found
    page         INT,
    total_checked INT        NOT NULL,
    status       TEXT        NOT NULL, -- ok | not_found | error
    checked_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON rank_check (sku, checked_at DESC);
```

Алерт: после записи сравниваем с предыдущей позицией; если была ≤50, стала >50
(или not_found) — шлём в Telegram (с дебаунсом, чтобы не спамить).

## 4. Риски и снижение

| Риск | Снижение |
|------|----------|
| Массовый бан прокси | Резидентные IP, ротация, cooldown, адаптивный rate limit, запас по пулу. |
| Смена вёрстки/антибота Ozon | Селекторы и логика в одном месте; алерт на рост доли `error`; быстрый патч. |
| Дороговизна резидентных прокси | Кешировать выдачу (одна выдача → много SKU за один проход), не дёргать каждый SKU отдельным запросом. |
| Пики нагрузки / долгие задачи | Очередь + автоскейл воркеров, таймауты, идемпотентные ретраи. |
| Потеря данных | PostgreSQL с бэкапами; задачи идемпотентны (uniq по sku+день). |
| Юридические/ToS | Только публичные данные, умеренные лимиты, никакого DDoS-поведения. |

**Оптимизация по делу:** 20 запросов общие на все 500 товаров. Значит выгодно
группировать по запросу: один проход выдачи (до 100 позиций) закрывает сразу все
SKU, которые в ней есть. Это снижает 10k «проверок» до ~20 проходов × N страниц —
кратная экономия прокси-трафика.

## 5. Бюджет (ориентир, в месяц)

| Статья | Вариант | Цена |

| Резидентные прокси | ~50–100 IP / трафик-пакет | **$30–80** |

| PostgreSQL | managed small или на том же VPS | **$0–15** |
| Redis | на том же VPS | **$0** |
| Мониторинг | self-hosted Grafana/Prometheus | **$0** |

Для 10k/день реально уложиться в **~$50–60**, если брать трафиковый тариф прокси
и группировать проверки по запросу.
